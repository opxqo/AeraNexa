# AeraNexa 节点二级市场任务计划报告

> 版本：讨论稿，2026-09-26。依据 [`node-market-design-notes.md`](./node-market-design-notes.md) 与当前代码静态核对编写。**本文是实施计划，不代表已获准开发或上线。**
>
> 本轮明确约束：**第一阶段不考虑提现**。后续是否开放提现未定，不在本计划的交付范围内；不得把“暂不提现”推断成“永久不提现”。

## 1. 目标、边界与结论

目标是验证“卖家自有 VPS 接入 AeraNexa，买家使用付费套餐流量，平台依据可核对用量给卖家记站内收益”是否同时具备产品需求、可运行的技术链路和可承担的成本。

建议采用 **封闭技术验证 → 限量邀请试点 → 评估是否开放准入** 三道门。第一道门可不接真实买家、不发生结算；第二道门若仍只有卖家控制的计数，只能用测试账号和模拟/影子账本验证，不能因人工抽查就扣真实买家流量或释放卖家可用收益。第三道门需要证明计量、纠纷和运营机制可持续。

本计划不包含：提现、公开卖家注册、保证金自动扣罚、AI 自动处罚、跨节点通用买家凭据、以“无退款”替代拒付处置。自营节点仍走 3x-ui 主控；卖家节点直连 AN 的方案作为待验证架构，不把接口路径相同视为兼容性已通过。

## 2. 当前基线与差距

| 领域 | 当前可核对状态 | 二级市场需要补的能力 |
| --- | --- | --- |
| 节点连接 | `src/lib/server/panel/client.ts` 读取一套全局地址和 Token；六个 API 在本地白名单内 | 每卖家节点独立地址、Token、证书指纹、连接状态及权限边界 |
| 凭据 | `users.uuid` 在自营入站复用；`src/lib/server/panel/sync-model.ts` 支持 vless/vmess/trojan | 买家 × 卖家节点独立 VLESS 凭据；撤销单节点凭据不影响自营节点 |
| 流量 | `src/lib/server/panel/collect-traffic.ts` 将用户合计增量写入 `users`，自营节点量只作统计；worker 默认每 60 秒采集 | 卖家节点按买家、节点和计数世代记账；断线、重置、重复采集可对账 |
| 套餐流量 | 用户当前只有 `transfer_enable` 与已用总数，订阅和 worker 都按总量判断 | 区分付费可用、赠送/试用/邀请来源；卖家节点只消耗合格额度 |
| 钱包 | `users.balance` 与 `wallet_transactions` 支持支付入账、充值卡和消费；另有 `commission_balance` | 卖家收益独立账本与可用状态；不得直接混入可换卡、可转让或其他未审查的出口 |
| 运行 | `pnpm worker` 独立进程串行跑同步、采集、订单处理等任务，靠 MySQL 命名锁选主 | 卖家节点单独隔离故障与重试，避免一个卖家节点拖慢自营节点和订单任务 |
| 精简节点 | `source/3x-node` 有管理 API、VLESS 和本地采样；路径静态比对通过 | 实际请求/响应、TLS、凭据、断线恢复、流量语义及资源占用实测 |

这些是本次阅读代码得出的设计基线，不是上线验收结果。现有工作区可能有其他未提交变更；实施时需重新确认分支和最新代码。

## 3. 关键决策：在排期前定口径

| ID | 需要负责人确定的事项 | 建议默认值 | 决策影响 |
| --- | --- | --- | --- |
| J1 | 试点是否让真实买家扣流量、卖家入账 | **仅测试账号影子记账**；若要真实结算，先取得独立计量并通过新的门槛 | 决定计量和账本的最低门槛 |
| J2 | 付费流量如何识别 | 每次已确认付款产生独立来源批次；免费流量单独批次 | 防止普通总额度混用 |
| J3 | 卖家收益可买什么 | 仅允许明确列出的站内服务；充值卡、转让及其他出口默认关闭 | 决定钱包隔离和反套利范围 |
| J4 | 标价上限 S1 | 只在确定计价口径后启用；先用管理员审核价 | 需处理折扣、活动、永久套餐、流量重置和存量套餐 |
| J5 | 卖家节点管理连接方向 | 第一版先评估 AN 主动连接；记录 NAT、来源 IP 暴露和可达性结果 | 影响节点部署、证书固定及网络成本 |
| J6 | 试点参与者、流量和损失上限 | 负责人名单制，小规模、可随时停用；具体数值试点前定 | 决定真实资金/流量风险范围 |
| J7 | 经营地、卖家/买家所在地及服务形态 | 上线前由合规专业人士核实 | 决定是否可对外经营及服务条款 |

“无提现”只回答资金出口的一部分。任何商品、充值卡、转让、赠送或代付路径，都要按 J3 逐项审查。

## 4. 分阶段任务清单

### 阶段 A：设计冻结与封闭验证（无真实结算）

| ID | 任务与产物 | 前置 | 验收标准 |
| --- | --- | --- | --- |
| A1 | 将 D1–D7、S1–S4 和 J1–J7 做成决策记录，标明负责人、日期、版本 | 无 | 无“建议”被误写成“已拍板”；第一阶段不提现被明确记录 |
| A2 | 绘制资金与流量两套状态图：买家额度来源、冻结、消耗、冲正；卖家待复核、可用、撤销 | A1 | 能解释订单退款/拒付、套餐重置、节点断线、计数回退及争议时每笔账的去向 |
| A3 | 建 3x-node 与 AN 的接口契约表，并在隔离环境跑真实联调 | 无 | 六个接口逐项记录请求、响应、认证、错误码；验证新增/更新/摘除/删除客户端的幂等和部分失败 |
| A4 | 验证真实流量计数：单用户、多用户、两个入站、上下行、重启、重置、断线、重复轮询 | A3 | 原始读数和独立测试流量有可复现记录；明确读数归属与误差，不以路径兼容代替计量兼容 |
| A5 | 做安全验证：独立 UUID、TLS 指纹匹配/轮换、Token 泄露后的处置、卖家获取买家凭据的边界 | A3 | 卖家节点凭据不能用于自营节点；单节点撤销不影响其他节点；错误指纹与错误 Token 均拒绝连接 |
| A6 | 测试低配 Alpine 节点资源与可达性，并对主动连接/回连方案作取舍 | A3 | 留存内存、CPU、重连、NAT 和来源 IP 暴露结果；给出可支持的最低规格而非沿用宣传规格 |
| A7 | 对经营许可、卖家机房/VPS 服务条款、出口 IP 责任和隐私告知做专业核查 | A1 | 有书面结论、负责人与适用地区；有阻断项时不得进入真实用户试点 |

**阶段 A 退出门槛**：A3–A6 可重复通过；A2 账务口径无未定义路径；A7 没有阻断真实试点的结论。未达到时只保留封闭实验。

### 阶段 B：平台基础能力（仍不开放卖家）

| ID | 任务与产物 | 前置 | 验收标准 |
| --- | --- | --- | --- |
| B1 | 新增卖家、节点归属和邀请/审批状态模型；保留自营节点字段及行为 | A1、A6 | 未获邀者无法接入；停用卖家或节点立即停止新订阅和新凭据发放 |
| B2 | 实现每节点独立的连接配置、密钥存储、TLS 指纹校验和有限 API 权限 | A3、A5 | 配置不可从买家 API 泄露；一台卖家节点故障不会让自营 worker/订单处理整体暂停 |
| B3 | 实现买家 × 卖家节点独立凭据与订阅渲染 | A5、B1 | 同一买家在两卖家节点和自营节点的凭据互不复用；撤销后旧凭据不再可用 |
| B4 | 建流量来源批次与合格额度规则 | A2、J2 | 免费来源在卖家节点不可用；续费、排队套餐、流量重置及并发使用可一致扣减；历史存量额度有明确迁移策略 |
| B5 | 建逐节点计数游标、计数世代和原始事件留痕 | A4、B1 | 重复采集不重复扣费；重置与重建不把旧流量当新流量；能按买家、卖家节点、时间追溯 |
| B6 | 做预授权/额度上限与断开策略；定义采集延迟的最大超额暴露 | B3–B5 | 多节点并发不能超额占用同一付费额度；断线/超时按既定策略停用；实测最大超额小于 J6 预算 |
| B7 | 建卖家收益独立账本：待复核、可用、撤销；定价快照、结算批次、唯一键和冲正 | A2、J3、B5 | 同一用量事件至多结算一次；买家扣量与卖家待复核收益在可审计事务中对应；现有余额出口不可绕过限制 |
| B8 | 建后台操作与告警：邀请、节点审查、暂停、收益复核、账本对账、紧急关停 | B1–B7 | 管理员可在不改数据库的情况下暂停节点及收益释放；操作留审计记录 |

**阶段 B 退出门槛**：自营节点回归正常；买家独立凭据、来源流量、并发预授权和收益账本的异常路径通过测试；未获邀用户看不到试点入口。若 J1 改为真实结算，必须先补足阶段 D 的可信计量门槛。

### 阶段 C：邀请制试点（限量、可撤销）

| ID | 任务与产物 | 前置 | 验收标准 |
| --- | --- | --- | --- |
| C1 | 选定卖家与买家名单、节点地域、试点时长、每人/每节点用量与金额上限 | B 阶段、J6、A7 | 名单、上限、责任人和退出方式可查；参与者理解第三方出口 IP 与连接元数据边界 |
| C2 | 完成卖家接入指引和买家展示页：价格、节点归属、服务质量、隐私提示 | B1–B3 | 卖家能自助提交、管理员审核；买家能区分自营与卖家节点并看到收费规则 |
| C3 | 先影子计费：只计算应扣流量与待复核收益，不释放可用余额 | B4–B8 | 连续样本能与独立测量对账；差异、掉数、重试、断线有记录和处理结论 |
| C4 | 试点升级评审：有独立计量时才开启限量真实使用、人工复核结算及申诉/冲正；否则继续测试账号影子账本 | C3、A7、J1、D1 的可信计量验证 | 每批真实结算有独立计量、规则版本、复核人和释放记录；缺证据则不扣真实买家流量、不释放收益 |
| C5 | 做试点评估：测试账号留存、节点可用率、成功连接率、用量差异、工单、单位成本、管理员时间；如开展 C4，再纳入真实买家指标 | C3；C4 可选 | 出具继续/缩小/停止建议；不以流量规模单一指标判定成功 |

**阶段 C 停止条件**：发现卖家可跨节点复用买家凭据、批量虚报无法识别、账本无法对平、合格流量可被免费来源绕过、出现监管/服务条款阻断，或实际损失超 J6 上限。停止时先停发新凭据和收益释放，保留审计记录，再按预设规则处理已发生账务。

### 阶段 D：是否扩大开放（单独决策，不随试点自动开启）

| ID | 任务与产物 | 前置 | 验收标准 |
| --- | --- | --- | --- |
| D1 | 选可信计量方案：平台中转计量优先评估，同时测算带宽、延迟、故障点和地域成本；如要在 C4 真实结算，须提前完成 | A4、C3 的影子数据；全面成本评估还需 C5 | 能独立于卖家机器取得可审计用量；成本仍符合产品定位 |
| D2 | 若需开放准入，设计保证金、账户年龄、付费记录、审核、申诉及人工处罚流程 | C5、D1 | 保证金冻结后不能被花掉；扣罚必须有证据与人工确认；金额 S2 仍需负责人批准 |
| D3 | 确定标价上限 S1 的计算规则与异常处理 | C5 | 明确折扣、免费赠送、永久套餐、流量重置、价格变更及历史订单；不会出现可循环套利组合 |
| D4 | 增加异常规则与调查报告；AI 仅汇总证据，不自动处罚 | D1–D3 | 报告引用可信计量和原始事件；卖家可控文本按不可信输入处理；管理员能复核 |
| D5 | 依据试点与合规结果做开放准入决策 | D1–D4、A7 | 有书面批准、容量/损失预算、故障预案和回退路径；未获批准则维持邀请制 |

## 5. 建议实施顺序与依赖

```text
A1 决策与 A2 账务口径 ─────────────┐
A3 接口联调 → A4 计量 / A5 安全 / A6 资源 ├→ 阶段 A 门槛
A7 合规核查 ────────────────────────┘
                    ↓
B1/B2 节点接入 → B3 凭据 ─────────┐
B4 来源额度 → B5 逐节点计数 → B6 预授权 ├→ B7 收益账本 → B8 后台 → 阶段 B 门槛
                    ↓
C1/C2 名单与展示 → C3 影子计费 ──→ C5 评估
                       ↓                ↑
                  D1 独立计量 → C4 真实结算
                       ↓
                  D2/D3/D4 → D5 开放决策
```

粗略工作量按 **1 名熟悉项目的全栈开发者 + 可用的节点测试环境**估算，仅用于排优先级：阶段 A 约 1–2 周，阶段 B 约 4–8 周，阶段 C 至少 2–4 周观察，阶段 D 取决于可信计量方案与合规结论。资源、联调故障和方案变更会显著改变日程；不要把它作为交付承诺。阶段 A 的技术验证、账务设计和合规核查可部分并行；真实试点必须等待全部门槛通过。

## 6. 测试矩阵与交付证据

| 类别 | 必测情形 | 留存证据 |
| --- | --- | --- |
| 协议兼容 | 六接口正常/错误响应、Token 失效、证书轮换、重定向、超时 | 契约记录与脱敏日志 |
| 凭据隔离 | 卖家读取本机配置、旧凭据撤销、跨节点重放、自营节点误用 | 拒绝连接结果和订阅样例 |
| 计数 | 上下行、重启、重置、并发、重复采集、计数器回退、时间边界 | 原始快照、独立测量与差异报告 |
| 额度 | 付费/试用/赠送混合，续费、排队、重置，两卖家节点同时消耗 | 额度流水与不变量检查 |
| 钱包 | 重复事件、冲正、争议、充值卡/转让出口、人工复核 | 买家用量与卖家收益双向对账 |
| 故障 | 卖家节点离线、恶意慢响应、worker 重启、数据库回滚 | 恢复时间、自营节点与订单任务不受拖累的记录 |
| 产品 | 买卖双方能理解价格、节点归属、隐私与申诉 | 可见页面验收和试点反馈 |

完成每阶段时至少交付：决策记录、版本化的数据/接口契约、测试结果、剩余风险、是否通过门槛的书面结论。实施中的代码门槛按项目现有 `pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm build` 执行，并补真实节点联调；纯 HTTP 200 或单元测试不能替代功能验证。

| 优先级 | 风险 | 当前判断 | 处理 |
| --- | --- | --- | --- |
| P0 | 卖家控制计数，虚报真实买家用量 | 未解决；抽查只能辅助发现 | 阶段 C 先影子计费；任何真实结算前取得独立计量 |
| P0 | 卖家读取买家凭据后跨节点使用 | 当前全站 UUID 架构不满足隔离 | B3 前不接真实卖家节点 |

| P0 | 卖家收益进入现有通用余额后出现意外出口 | 不提现仍有换卡、转让、代付等待审查路径 | B7 使用独立账本和用途白名单 |
| P1 | 60 秒采集周期与并发造成透支 | 当前按周期停用，非实时预授权 | B6 预留上限、实测最大暴露并设置关停阈值 |
| P1 | 3x-node 路径兼容但载荷/计数语义不兼容 | 仅静态比对 | A3/A4 实机验证 |

| P2 | 中转计量成本吞噬低价资源共享收益 | 尚无测算 | D1 先算再决定是否扩大 |

## 8. 第一批可执行工作包

在负责人决定开始工作后，按以下顺序立项，避免一开始就做完整市场 UI：

1. **验证包**：A3–A6，产出兼容性和计数证据；不接真实买家、不记卖家收益。
2. **规则包**：A1–A2、J1–J7，定清额度来源、收益可用性及风险预算。
3. **基础包**：B1–B8，通过封闭环境验收后才进入邀请试点。
4. **试点包**：C1–C5，按每批记录做复核，得出真实成本与风险数据。

建议当前最近一步是完成 **A1/A2 的决策表和 A3/A4 的本地联调**。其中联调可以不改变 AeraNexa 生产逻辑；是否开启这一工作包，应由负责人在讨论结束后明确安排。

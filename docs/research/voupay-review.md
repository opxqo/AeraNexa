# VouPay 源码只读审阅

审阅日期：2026-09-21  
审阅对象：[`voucash/voupay`](https://github.com/voucash/voupay) 提交 `d9391bc33ed22d387540b98de23f6db9f5d10f25`。本地以 `--depth 1` 克隆后确认 HEAD 与指定提交一致。本文只根据该提交内可见文件和其维护者提供的公开接入说明作出结论；VouPay 的服务端、`voupaysdk.js`、验证 API 与实际清结算系统均不在仓库中，不能从源码验证。

## 结论

VouPay **不是可自行部署的支付网关**，而是一个极薄的浏览器 SDK 接入仓库：商户网页从 `voupay.io` 加载远程 JavaScript，将订单号、金额、币种和回调 URL 交给该 SDK；VouPay 托管收银台及其服务端处理用户付款，并向商户回调。它宣传支持礼品卡、USDT（TRC20/ERC20）和 BTC，但仓库中没有 USDC、链上地址派生、交易监听、确认数、私钥/助记词管理或退款实现。

因此，它可作为一个外部、中心化的收款服务候选项来评估，**不能**作为 AeraNexa 的“BTCPay/自托管 USDC 网关”替代品，也不能仅凭这个仓库证明资金安全、KYC/合规、实际支持的币种网络或可用性。

## 可见架构与技术栈

```text
浏览器（商户站）
  └─ <script src="https://voupay.io/voupaysdk.js">
       └─ SDK / VouPay 托管收银台（源码未公开）
            ├─ 礼品卡或加密货币付款（具体实现未公开）
            └─ POST 商户 callbackUrl
                 └─ 商户服务端再 POST https://voupay.io/api/verify
                      └─ 商户按验证结果更新订单
```

仓库只有三个文件：Markdown 接入说明、PHP 回调示例和 README；没有 `package.json`、后端服务、容器编排、数据库 schema、Dockerfile 或部署清单。所谓 SDK 是通过远程 `<script>` 直接加载，而非仓库内构建产物（`API.md:9-30`）。这意味着实际技术栈、可部署组件、监控、备份、钱包和节点均不可见，也无法自行在本地或独立服务器复现。

## 付款方式与加密货币链路

- README 将产品称为“前端支付 SDK”，并声称用户可使用“礼品卡或数字货币”付款（`README.md:12-19`）。列出的方式是京东 E 卡、Steam 充值卡、`USDT (TRC20/ERC20)`、BTC；**未列出 USDC**，亦没有代币合约地址或确认策略。
- SDK 初始化的输入是由浏览器传入的 `orderId`、十进制 `amount`、`currency`（文档只声明 `CNY` / `USD`）及商户 `callbackUrl`（`API.md:14-21`、`API.md:37-46`）。文档没有商户 API Key、签名、服务器端创建 invoice，或支付方式/网络选择参数。
- README 说商户后台会取得平台“现金券”，然后到 `voucash.com` 控制台提现 USDT 或加密货币（`API.md:51-55`）。这表明清算和提现依赖 VouPay 平台账户，而不是商户自持 USDC 地址或链上自动结算。
- 文档称付款后通常延迟 3–5 个工作日，先回调“提醒发货”，1–3 天后才再次回调现金券或退款结果（`API.md:53-55`）。这不是即时、最终链上确认模型；交付与商户资金可用性存在平台审核/争议期。

## Webhook 与密钥安全

可见的 PHP 示例接收任意 JSON 回调后，把**同一份原始报文**转发给 `https://voupay.io/api/verify`，并仅在返回 `{ "valid": true }` 时接受（`callback.php:10-18`、`callback.php:27-53`）。本仓库未披露下列关键内容：

- Webhook 签名算法、签名头、时间戳/nonce、防重放窗口、平台公钥或证书轮换；
- `/api/verify` 如何将这份报文与真实事件绑定，以及其认证、限流、审计与可用性；
- SDK 如何向 VouPay 创建订单，及该请求是否防止客户端篡改金额、订单号和回调地址；
- 钱包私钥、助记词、热冷钱包隔离、多签、链节点、充提风控与资金托管责任。

该设计把回调真实性的最终判断外包给 VouPay；商户不持有可离线验证的签名材料。`/api/verify` 故障会使商户无法安全处理回调（示例会返回 HTTP 500，`callback.php:41-44`）。

示例还要求商户自行查本地订单、比对金额和币种，但这段防护代码被注释，未构成可运行的默认实现（`callback.php:55-72`）。它也没有持久化事件 ID、唯一约束或事务幂等，因此同一回调重投时若照抄示例可能重复履约。

最严重的语义问题是：说明称 `paid` 只是“用户已完成付款（还需要平台最终确认）”，`completed` 才是“平台已放款”（`callback.php:74-75`），但紧接着示例把 `completed` **和 `paid` 都当作支付成功并建议发货**（`callback.php:75-80`）。AeraNexa 绝不能沿用这个判断：只能将平台明确的最终、不可逆成功状态映射到 `settleOrder()`，并以数据库幂等锁执行一次。

此外，示例以 `floatval()` 读取金额（`callback.php:55-59`）。生产实现应使用订单创建时保存的整数最小货币单位或精确十进制定点值，不能以二进制浮点作安全对账。

## 与 AeraNexa 的适配边界

若经过独立的商业、地区和合规审查后仍选择试点，AeraNexa 应将其视为一个 **第三方、托管、延迟结算的支付方式**，而非链上钱包：

1. 服务器端保存站内订单金额/币种；浏览器只拿不可篡改的支付会话或由服务端签发的订单引用。不要以 SDK 传入的 `amount` 作权威值。
2. 回调仅入库为原始事件；随后主动核验、关联本地订单、验证金额/币种/终态、记录渠道事件唯一标识，并在单一事务内幂等履约。`paid` 应保持待平台最终结算，除非对方书面 API 合约明确定义其为最终态。
3. 不把任何 VouPay “现金券”当作用户支付交易哈希；将商户可提现余额/券与用户订单付款分开建账。
4. 上线前要求提供正式、版本化的服务端 API/Webhook 文档和测试环境，明确签名/重放保护、状态机、重试、退款/拒付、订单查询、网络与资产（特别是是否为原生 USDC 及具体链/合约）、资金托管、KYC、地域与服务条款。
5. 即使接入，也保留卡密/人工审核作为支付失败、审核拒绝和提现延迟时的运营兜底；不要将平台“匿名”宣传语转化为 AeraNexa 的合规或安全承诺。

## 风险摘要

| 风险 | 依据 | 对 AeraNexa 的影响 |
| --- | --- | --- |
| 黑箱第三方与单点依赖 | 收银台、验证与提现均指向 `voupay.io`，服务端未开源（`API.md:12`、`API.md:51-55`） | 无法自托管；可用性、账务和资金取决于供应商。 |
| 终态/交付错配 | `paid` 尚需最终确认，但示例又建议其发货（`callback.php:74-80`） | 可能在审核拒绝或退款前开通权益。 |
| 回调完整性不可审计 | 无本地签名规范，只有远程 verify 示例（`callback.php:27-53`） | 需先取得供应商协议，不能直接信任前端成功回调。 |
| 账务和重复履约 | 本地金额校验被注释，缺少幂等示例（`callback.php:55-72`） | 必须用现有 AeraNexa 交易账本与幂等履约补足。 |
| 加密资产能力未证实 | 仅文字声明 USDT 两网络/BTC，未有 USDC 或链上实现（`README.md:16-19`） | 不能据此承诺支持 USDC 或自动链上确认。 |

## 审阅范围与复核建议

本结论是对指定 Git 提交的源码审阅，不是对 VouPay 运营方的信誉、资金安全或合法性的背书/否定。下一步若要真正集成，先索取并以测试订单验证其服务端订单创建、签名 Webhook、主动查单、最终结算、拒绝/退款和 USDC 网络合约；在这些证据到位前，建议不接入生产自动履约。
